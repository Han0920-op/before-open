# 未开张：场景与经营过程体验改版方案

日期：2026-10-26。状态：**第一批已实现，后续批次仍为设计计划**。实施范围与验证见 [第一批报告](SCENE_SANDBOX_REPORT.md)。

依据：用户本轮反馈“配置 Agent 增加难度、模拟只有数据，应该有具体场景和经营过程”；根目录 V4.0 第 0、3、5、6、10 节；[校园比赛评分参考](COMPETITION_RUBRIC.md)。

V4.0 原文保留。本文记录用户最新体验方向对实施顺序的调整：将二维场景与经营过程提前，普通用户不再配置模型；底层仍保留三类经营模型、确定性计算、单 Agent、来源标记、不可变方案和现实验证。本文不是已完成功能说明，也不把评分目标表述为已获分数。

> 2026-10-27范围更新：用户决定暂不接入AI，下文默认服务和Agent流程保留作扩展设计，不属于当前交付。当前以手动确认条件的场景经营为主，详见[AI延期说明](AI_DEFERRED.md)。

## 1. 改版目标与当前问题

用户应该能体验：“我在这里做这门小生意，作出一个选择，看到经营过程怎样变化，再换个选择试一次。”

现有代码中的主要问题：

- `ModelConnector` 位于全站导航，用户先理解服务商、模型、API Key、费用授权，才可能使用 Agent；这是先前自带 Key 路线产生的体验成本，本轮方向调整为运营方提供默认服务。
- `Setup` 同屏铺开 AI 准备和完整手动表单，重复入口、字段过多。
- `Sandbox` 主要是 `SceneFields` 和 `Results`，展示期末结果，缺少空间、过程与可操作对象。
- `AgentAnalysis` 需要用户额外点击；工具能力没有自然融入经营任务。
- 现有 `calculate_perishable / calculate_durable / calculate_service` 是一期总量计算，**尚没有分时段经营状态机**。加动画不等于已经具备过程计算。

## 2. 新主流程

**说想法 → 看见场景草稿 → 确认少量经营条件 → 筹备 → 分段营业 → 收摊 → 换方案 → 现实验证。**

首页保留一句话输入和三个示例。自定义想法由默认后台 Agent 提取，不要求用户选行业模型；不支持的业务明确提示边界。例子是体验入口，自定义描述仍能改变标题、商品、地点说明、客群和经营条件。

准备页只显示“已经知道”“还差什么”“先用演示条件”三组内容，一轮最多追问三项。成本、数量等不能计算所需的空值必须补齐或经用户主动选择演示假设；预算未知仍可推演，但不判断钱是否够。提供逐项编辑与展开全部条件，避免强制长表单。

## 3. Agent 如何退出配置流程、融入体验

| 场合 | 用户看到的内容 | 后台职责 |
|---|---|---|
| 输入想法 | “我先帮你搭个场景”及真实任务状态 | 事实提取、类型匹配、识别未知 |
| 准备开摊 | “还需要确认每份成本” | 最多三项澄清、校验草稿 |
| 筹备 | “这批备货需要的资金超过预算，想换个数量试试吗？” | 调用预算与经营工具，依据真实结果提示 |
| 营业节点 | “按这组需求假设，库存已经用完” | 确定性过程引擎触发；需要解释或方案建议时再使用 Agent |
| 收摊 | “剩余多少、为什么、下一次可改什么” | 汇总真实台账，提出分支或现实任务 |

具体调整：

- 从普通用户导航移除“模型接入”，不在首次体验出现 Key、模型名或 Agent 参数；不另建普通用户的 Agent 配置页。
- 使用已有服务端模型设置建立运营配置；服务商和凭据由运营者配置，密钥不进入前端包。开发环境可保留明确隔离的调试入口，已有接入逻辑不直接删除。
- 自动化只发生在用户主动开始的本次任务中；不为每帧动画、每次拖动调用模型。程序可直接完成的数值提示走规则，不伪装成 AI 分析。
- 已确认的经营条件发生变化，仍需用户确认新方案；普通“下一阶段”推进不反复要求确认同一条件。
- 尚未配置服务或服务不可用时，提示“智能整理暂不可用”，提供演示场景和手动调整；不能在移除 Key 入口后假定 AI 自动可用。
- 默认真实模型需要运营方的可用服务、网络和费用预算。上线前补齐服务端总调用/Token 配额与限流，达到限额后停止 AI 请求；现有单次工作流限制不等于整站费用封顶。可视沙盒本身不依赖模型连接。
- 实际工具记录保留在“为什么这样说／查看依据”中，默认展示中文摘要。

## 4. 沙盒界面：以场景为主，以数字为辅

采用轻量二维俯视或斜视插画，SVG／DOM＋CSS 实现；先不引入游戏引擎。沿用奶油白、暖橙和鼠尾草绿设计系统。

```text
我的校园冰粉摊       方案 A       筹备 → 开摊 → 营业 → 收摊
┌────────────────────────────────────────────────────┐
│ 校园周末市集 · 地点示意       当前条件：演示需求假设   │
│                                                    │
│  市集环境       顾客符号 → 价签／摊位 → 取货位置      │
│                             货架：剩余 22 份        │
│                                                    │
│  点击价签改价格，点击货架定备货；操作随阶段显示        │
└────────────────────────────────────────────────────┘
 已卖 8 份       库存 22 份       已收 ¥72       已支 ¥225
 本轮提示：还剩两个营业阶段，可以继续看看，也可另试方案。
 [下一阶段] [自动播放／暂停] [另试一种方案] [查看依据]
```

上图只说明布局。示例数字依据单价 9 元、成本 3.5 元、备货 30 份、固定费 120 元；“已收”不是利润，“已支”不等于含预算的现金余额。

交互对象：

| 对象 | 筹备阶段可做什么 | 营业过程怎么表现 |
|---|---|---|
| 价签 | 点击编辑售价，明确需求假设不会自动随价格改变 | 展示已确认价格；改价入口解释为回到筹备新建方案 |
| 货架／备货箱 | 改备货，实时看采购支出与预算缺口 | 由实际阶段销售扣减；量大时用带数字的成组符号，不渲染成千商品 |
| 顾客／订单符号 | 选择少一些、当前、更多的需求假设并确认来源 | 仅表示本阶段假设需求或订单，不表示真实人流或购买意愿；符号代表数量需可查 |
| 收款位置 | 展示预计投入，不自动扣除真实资金 | 展示累计收入和支出，收摊再解释结果 |
| 经营条件卡 | 编辑费用、期间及当前需求条件，展开来源 | 当前条件固定；换条件必须明确另开方案或在后续过程版本中分支 |

桌面：场景占主要区域，右侧为当前任务与轻量提示，底部为三至四个核心指标。手机：场景上方显示当前阶段，下方只显示一个主要动作，细节放入抽屉。场景中的点击对象也有键盘可达的等价按钮。

支持暂停、逐步推进和快速看结果；减少动态效果时直接切换状态。画面速度不改变销量、时间或费用。动画期间用户也能读取文字台账。

## 5. 三种业务要呈现不同的经营过程

| 场景 | 空间与操作对象 | 经营过程 | 收尾重点 |
|---|---|---|---|
| 校园冰粉摊 | 摊位、价签、备货箱、取货区 | 准备一批商品→分段需求到来→售出／缺货→收摊 | 已投入整批成本、收入、未售易损耗商品；首版沿用“本批未售不可保留”假设 |
| 手工饰品摊 | 陈列架、价签、收纳箱 | 陈列备货→分段售卖→剩余商品收纳 | 分开显示现金变化、简化期间结果和仍持有库存 |
| 预约摄影 | 拍摄区、待服务订单、时间条 | 核对有效预约→按每单完整耗时推进服务→时间用完 | 完成单数、受限产能、空闲分钟；取消不等于已服务，不产生收费 |

场景会使用用户的商品名、描述和业务类型渲染配置，场景图层只从白名单组件组合。第一版不让模型自由生成可执行前端，也不依赖图片生成请求才能进入沙盒。不做自由装修、NPC 养成或虚拟货币。

## 6. 从“结果卡”走向“过程”的两步实现

### 6.1 下一开发批次：可操作的场景＋有状态的逐步推演

开摊前作出价格、备货、需求条件等选择，经确认后冻结。营业时每按一次“下一阶段”，服务端推进一个过程状态，返回本阶段变化与累计结果；暂停只暂停呈现，禁止重复结算。

零售分为三个**逻辑营业阶段**。现有数据没有小时级客流，默认不虚构具体钟点。总需求怎样分配到三段是一项新增的、明确显示的演示假设，用户确认后保存。例如总需求 12 份时，可以展示 4／4／4；其他总数采用有版本的整数均分规则，余数从前到后分配。它不代表真实客流规律。

固定费用和整批采购在筹备确认后记入一次推演台账；营业段依次处理需求，累计售出不得超过库存。摄影按完整订单所需分钟逐单推进，取消订单先剔除，超出产能的订单不产生收入；不额外编造日历时段、客户行为或退款规则。

每段画面都读服务端状态，且可刷新恢复。第一批营业中可继续、暂停、查看依据、结束动画直接看完整结算，或**“回到筹备，另试一个方案”**。这里“直接看结算”会计算全部剩余阶段，不是提前收摊；改价格／备货会从头运行新方案，不追改已经展示的交易。

这批次的交互重点是筹备决策、逐步观察、发现问题和对照重试，不声称已经支持任意营业中经营动作。

### 6.2 后续独立批次：营业节点上的分支决策

在第一批通过后，再增加“从当前节点试另一组后续需求条件”：用户确认新的后续需求计划，建立独立过程分支，复制此前台账，之后只影响未执行阶段。界面明确这是改变情景假设，不能说是促销导致销量增加。

营业中补货、调价、临时加单、提前收摊、天气事件均不混入第一批。它们分别涉及新采购、分段单价、时间或损耗等规则，需独立定义、确认和测试后再增加。若以后加入“下雨”，必须先展示用户确认的需求变化规则，不能由模型编造影响系数。

## 7. 一次冰粉推演的具体体验

用户说：“我有 500 元，想在学校周末市集卖冰粉。”

1. 自动出现校园摊位草稿，显示商品、预算、地点说明，询问成本、单价、备货；也可明确选用演示条件。
2. 用户选择示例：单价 9 元、成本 3.5 元、备货 30 份、固定费 120 元、总需求 12 份。上述示例值标记为假设，预算 500 元来自用户。
3. 筹备时点击备货箱可改变数量；确认后本轮需支付 225 元，预算余额 275 元，不显示成“已经亏损 225 元”。
4. 用户确认三段需求 4／4／4。第一段卖出 4 份：库存 26、累计收入 36 元；第二段库存 22、收入 72 元；第三段库存 18、收入 108 元。
5. 收摊显示本轮简化结果 -117 元，解释整批已发生成本与未售商品处理假设，并提出“回到筹备，试试少备一些”。这些数字必须与 V4.0 的固定算例一致。
6. 用户另试备货 15 份，保持价格、费用和总需求不变：收入仍为 108 元，需支付 172.50 元，简化结果 -64.50 元；保留原方案并说明改善来自备货支出减少，不能宣称方案已经盈利。
7. 用户选择一项现实任务，如询问实际材料报价。记录真实反馈和局限，经确认作为新方案条件复算；不把少量口头意愿直接换算成现实销量。

## 8. 技术复用与新增边界

继续复用：三种 SceneSpec、整数分金额、经营公式、来源验证、版本分支、比较、会话权限、CSRF、幂等、Agent 工具与 checkpoint、实验和观察存储。现有项目、结果、用户 Key 接入代码不删除，不清空数据库。

建议新增文件（设计清单，尚未创建）：

```text
frontend/src/scene/
  SceneStage.tsx              # 统一场景容器、阶段和交互入口
  RetailStall.tsx             # 两类零售的摊位／货架表现
  ServiceStudio.tsx           # 服务空间与时间条
  PreparationDrawer.tsx      # 点击对象后的短表单
  ProcessControls.tsx        # 下一步、暂停、查看完整结算

backend/app/simulation/process.py
backend/app/services/process.py

backend/alembic/versions/0003_process_runs.py  # 编号以实施时实际最新迁移为准

```

拟新增契约：

| 对象 | 必需内容与约束 |
|---|---|
| ProcessProfile | 过程规则版本、阶段列表、整数需求分配及来源与确认信息；分段合计须等于所选总需求；服务记录有效预约和每单耗时规则 |
| ProcessRun | 所属项目／场景版本／模拟快照、过程输入快照、规则版本、当前位置、状态、并发修订号；后续分支记录父过程与分支节点 |
| ProcessStep | 过程 ID、唯一序号、动作、处理的需求／订单、前后状态与整数分台账差值；追加保存，不覆写历史 |
| ProcessView | 当前库存／完成数、累计收入与费用、剩余服务时间（适用时）、合法下一步、中文摘要；不返回服务密钥 |

拟提供创建过程、读取过程、推进下一步、计算至结束四类 API；沿用项目所有权、写操作 CSRF 和幂等，推进携带预期修订号。重复点击不重复售出，并发冲突后重新读取；快进在服务端执行同一推进逻辑。普通逐步运行与 Agent 的节点／调用额度分别计数，不为每一步启动 Agent。

总量经营公式仍为权威：无额外决策的过程结束后，必须与同一输入的现有 SimulationSnapshot 对账。过程状态不要塞进 LangGraph checkpoint；新增数据经迁移落业务表。新过程规则使用独立版本，不改写旧模拟模型和旧快照。

## 9. 验收与评分证据

| 检查 | 验收要求 | 对应维度 |
|---|---|---|
| 无配置首次体验 | 普通页面无 Key／模型选择；有服务可直接整理；无服务可进入清楚标记的示例和手动路径 | 可用性 |
| 场景可操作 | 点击价签／货架／时间对象会出现真实编辑或解释；改变条件后画面和服务端结果一致 | 美观度、可用性 |
| 过程可信 | 每段状态可查；零需求、缺货、服务产能不足、取消均符合规则；无负库存，无重复收费；暂停／播放速度不影响结果 | 可用性、创新性 |
| 守恒与对账 | 每段售出总和、库存、收入、成本和分钟守恒；终态通过 V4.0 四个固定算例及三类业务回归 | 可用性 |
| 可恢复与可比较 | 刷新恢复；重复和并发推进不重复扣减；原方案和历史步骤不被重试、分支或动画覆盖；跨用户访问拒绝 | 可用性 |
| 标签清晰 | 假设顾客不是现实市场证据；分段需求来源可见；同条件比较不暗改需求；无真实工具时不展示 AI 已分析 | 创新性、可用性 |
| 移动端和无障碍 | 无横向溢出，文字、按钮可读可点；键盘替代入口；减少动态效果；低端设备不为大量商品创建大量节点 | 美观度、可用性 |
| 新手任务 | 5～10 位目标用户记录实际首次完成时间、独立完成情况、卡点及是否理解假设；目标 3 分钟内首次完整体验，未测试前不宣称达到 | 三项共同 |

## 10. 实施顺序与本轮范围

1. **第一交付**：普通用户免模型配置、准备页收敛、冰粉场景与服务端过程状态机，贯通筹备→逐段营业→收摊→从头另试方案；后端仍完整保留另外两类原有功能，不删除入口或历史。
2. **第二交付**：复用过程契约完成饰品、摄影专属表现，补齐手机、键盘、恢复和比较验证。三种类型全部通过后才声称改版完成。
3. **第三交付**：现实观察回到新方案与复盘，准备真实模型／新手评估及秒哒发布验证。再视评估需要推进营业节点分支，不先扩大事件系统。

设计提出时仅新增文档；后续第一批代码实施已完成，详见实施报告。真实模型服务与运营预算、赛事平台发布要求仍需落实。
